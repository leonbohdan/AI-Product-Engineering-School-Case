# ADR-0002: Стратегія крос-мовного зіставлення тем (Cross-lingual Entity Resolution)

- **Статус:** `Accepted`
- **Дата:** 2026-09-26

---

## 1. Контекст та постановка проблеми

Одна з ключових задач навички — порівняння попиту на тему в різних мовних регіонах (наприклад, запит із завдання: *«Порівняй зростання інтересу до інтервального голодування в польськомовній та чеськомовній Wikipedia за останні два роки»*).

Головна проблема полягає в тому, що:
1. Користувач формулює запит однією мовою (наприклад, українською або англійською).
2. Назви статей у Вікіпедії різними мовами є специфічними локалізованими термінами:
   - Польська: `Post_przerywany`
   - Чеська: `Přerušovaný_půst`
   - Англійська: `Intermittent_fasting`
   - Українська: `Інтервальне_голодування`
3. Прямий машинний переклад через словник або LLM часто повертає семантично схожі слова, але не точну назву статті у Вікіпедії, що призводить до HTTP 404 (стаття не знайдена).

Потрібен надійний механізм автоматичного знаходження точних назв статей у потрібних мовних розділах.

---

## 2. Критерії ухвалення рішення (Decision Drivers)

- **Точність (Hit Rate):** Мінімізація помилок 404 через неточні назви статей.
- **Автономність:** Агент або користувач не повинні вручну шукати точні URL статей у кожній Вікіпедії.
- **Підтримка ручного перевизначення:** Якщо тема специфічна або має кілька значень, користувач/агент повинен мати можливість явно передати точні назви.
- **Швидкість:** Пошук еквівалентів має відбуватися за лічені секунди.

---

## 3. Розглянуті альтернативи

### Варіант А: Переклад через LLM (Haiku / промпт)
- **Опис:** Агент генерує назви статей цільовими мовами на основі внутрішніх знань.
- **Мінуси:** Висока частота промахів: LLM може перекласти термін граматично правильно, але у Вікіпедії стаття може називатися інакше (синонім, уточнення в дужках тощо).
- **Оцінка:** *Відхилено як єдиний метод.*

### Варіант Б: Статичний словник (Hardcoded dictionary)
- **Опис:** Зашити в код відповідності для найпопулярніших тем.
- **Мінуси:** Працює тільки для заздалегідь відомих прикладів; не масштабується на довільні запити користувачів.
- **Оцінка:** *Відхилено.*

### Варіант В: Гібридний резолвер через Wikipedia Search + Wikidata Knowledge Graph (Обрано)
- **Опис:**
  1. Якщо вказана тема мовою запиту (наприклад, `uk` або `en`), резолвер робить швидкий пошук через Wikipedia OpenSearch API (`action=opensearch`) для вибору найбільш релевантної статті.
  2. За назвою статті отримується її **Wikidata Item ID** (Q-ідентифікатор, наприклад `Q3058848` для інтервального голодування).
  3. Через Wikidata API (`wbgetentities`) в один запит отримуються офіційні прив'язані статті (`sitelinks`) для всіх цільових мов (`plwiki`, `cswiki`, `dewiki` тощо).
  4. Забезпечується підтримка явного прапорця в CLI (наприклад, `--article-pl Post_przerywany`), якщо користувач хоче дослідити конкретну статтю.
- **Плюси:** 100% відповідність реальним статтям Вікіпедії; робота з будь-якою мовою без ручного налаштування; використання офіційного графа знань Wikimedia.
- **Мінуси:** Додатковий мережевий запит до Wikidata API перед викликом Pageviews API (компенсується кешуванням).
- **Оцінка:** *Прийнято.*

---

## 4. Обране рішення

Реалізувати модуль `scripts/topic_resolver.py`, який:
- Приймає тему (рядок) та список цільових мов (наприклад, `pl,cs`).
- Знаходить базову статтю та її Wikidata ID.
- Автоматично мапить офіційні назви статей у відповідних мовних версіях.
- Дозволяє перевизначення через словник або явні аргументи CLI.

---

## 5. Наслідки та компроміси

- **Позитивні:**
  - Користувач може ввести: *"порівняй інтервальне голодування в польській і чеській Вікіпедіях"*, і система знайде точні сторінки без помилок.
  - Усуваються помилки неіснуючих сторінок при виклику Wikimedia Pageviews API.
- **Компроміси:**
  - Якщо у певному мовному розділі статті на цю тему взагалі не існує, система має коректно повідомляти: *"Статтю не знайдено в розділі CS. Це свідчить про відсутність сформованого інтересу або низьку розвиненість розділу"*, що саме по собі є цінним продуктовим сигналом.
