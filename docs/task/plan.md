# План реалізації та аналіз кейсу: Wikipedia Trend Analysis Agent Skill

## 1. Формат реалізації: Чому «Джем-бота» (Gems / Custom GPT) недостатньо і потрібні скрипти

Використовувати лише «джем-бота» або виключно промпт у веб-інтерфейсі **категорично недостатньо** відповідно до прямої вимоги завдання (`skills/pes_task_1.md`, рядок 29):

> *«Навичка має містити `SKILL.md` та **власний код, який виконує змістовну частину роботи з даними**. Одного Markdown-файлу або інструкцій агенту щоразу самостійно написати потрібний код недостатньо... Не додавай скомпільовані виконувані файли; залежності та підготовка середовища мають бути відтворюваними. Усі власні матеріали й код мають бути в директорії навички.»*

### Чому необхідні локальні скрипти:
1. **Специфікація [Agent Skills](https://agentskills.io/specification):**
   - Навичка — це автономний пакет інструментів для AI-агентів (Claude Code, Cursor, Antigravity тощо).
   - Вона складається з двох компонентів:
     - `SKILL.md` (системна інструкція для LLM: опис інструментів, параметри, коли викликати, як інтерпретувати вивід).
     - Виконуваного детермінованого коду (CLI / скрипти), який виконує ресурсомісткі та точні операції.
2. **Точність та детермінованість:**
   - Веб-бот (LLM) не вміє безпомилково проводити складні математичні обчислення (розрахунок темпів зростання, ковзні середні, детекцію викидів) на масивах у тисячі чисел без ризику галюцинацій.
   - Скрипти виконують розрахунки на 100% точно, викачують дані з API, генерують графіки та компілюють валідний односторінковий PDF.
3. **Економія контексту та бюджету токенів:**
   - Передача LLM сирого JSON з переглядами за 2 роки (730 точок даних на кожну мову) забиває контекстне вікно моделі та коштує зайвих грошей.
   - Скрипт агрегує дані та повертає агенту лише компактні підсумкові метрики та шлях до згенерованого PDF.

## 2. Продуктовий аналіз кейсу (Product Engineering фокус)

Кейс фокусується на допомозі фаундерам B2C-продуктів ухвалювати інвестиційні рішення. Відповідно, аналіз має закривати ключові продуктові питання:

| Продуктовий виклик | Як це вирішується в коді навички |
| :--- | :--- |
| **Крос-мовне зіставлення тем** | Користувач вказує тему однією мовою (наприклад, англійською чи українською), але порівняння потрібне для інших мов (наприклад, польської та чеської). Скрипт автоматично шукає назви відповідних статей у різних мовних розділах через Wikidata API / Wikipedia Langlinks. |
| **Новинний шум vs органічний інтерес** | Короткочасні спалахи уваги (смерть відомої особи, скандал, фільм) не означають готовності аудиторії купувати продукт. Алгоритм розраховує 30-денне медіанне згладжування, виявляє аномальні сплески (Spike Ratio) і оцінює базовий органічний тренд. |
| **Метрика довіри (Reliability Score)** | Допомагає агенту відповісти на питання: *«наскільки цьому зростанню можна довіряти?»*. Якщо стаття має малий абсолютний обсяг (наприклад, 10–20 переглядів на день), зростання на 80% є статистичним шумом, а не ринковим сигналом. |
| **Фільтрація ботів і скрейперів** | У запитах до Wikimedia REST API параметр `agent` обов'язково встановлюється у значення `user`, виключаючи трафік ботів (`spider` / `automated`), який спотворює оцінку ринку. |
| **Оптимізація під легкі LLM (Claude Haiku 4.5 / OpenRouter Free)** | Інструменти мають лаконічний CLI-інтерфейс з передбачуваними аргументами. Скрипт повертає чітко структурований JSON зі зведеними показниками, що дозволяє навіть дешевим моделям давати глибокі й точні продуктові висновки. |

## 3. Рекомендована архітектура та структура проєкту

Для реалізації обираємо **Python 3.10+**, оскільки він має найкращу екосистему для статистичного аналізу даних, побудови графіків та створення PDF-звітів.

```text
skills/wikipedia-trend-analyzer/
├── SKILL.md                 # Опис навички за стандартом agentskills.io для LLM-агента
├── requirements.txt         # Відтворювані залежності (requests, pandas, matplotlib, reportlab)
├── run.py                   # Головний CLI-оркестратор (точка входу для виклику агентом)
├── scripts/
│   ├── wikimedia_client.py  # Отримання даних з Wikimedia Pageviews API з фільтрацією ботів
│   ├── topic_resolver.py    # Автоматичний резолв назв статей різними мовами через Wikidata
│   ├── trend_analyzer.py    # Розрахунок YoY/MoM, детекція спайків, розрахунок Confidence Score
│   ├── chart_generator.py   # Побудова наочного графіка динаміки переглядів (PNG)
│   └── pdf_generator.py     # Генерація 1-сторінкового PDF-звіту (Executive One-pager)
└── tests/
    └── test_cases.py        # Тести на 3 базових сценаріях із завдання
```

## 4. Покроковий план виконання (Roadmap)

### Етап 1: Модуль взаємодії з Wikimedia API (`wikimedia_client.py`)
- Реалізувати запити до `https://wikimedia.org/api/rest_v1/metrics/pageviews/per-article/`.
- Додати обов'язковий заголовок `User-Agent` (згідно з політикою Wikimedia API).
- Встановити параметри: `access=all-access`, `agent=user`, `granularity=daily`.
- Додати обробку перенаправлень (redirects) та нормалізацію URL-закодованих назв статей.

### Етап 2: Крос-мовний резолвер тем (`topic_resolver.py`)
- Реалізувати пошук еквівалентів назви статті в інших мовних розділах за допомогою Wikipedia API (`action=query&prop=langlinks`) або Wikidata ID.
- Підтримати ручне перевизначення назв статей, якщо автоматичний переклад неточний.

### Етап 3: Аналітика трендів та індекс довіри (`trend_analyzer.py`)
- **Метрики обсягу:** сумарні перегляди за рік/період, середньодобові перегляди.
- **Динаміка зростання:** розрахунок YoY (рік до року) та MoM (місяць до місяця).
- **Фільтрація аномалій:** виявлення спалахів (днів, де перегляди перевищують $3 \times \text{IQR}$ або медіану).
- **Індекс довіри (Reliability Score, 0–100%):** зважена оцінка на основі абсолютного обсягу трафіку, стабільності часового ряду (коефіцієнт варіації) та частки спайків.

### Етап 4: Генерація чартів та 1-сторінкового PDF (`chart_generator.py`, `pdf_generator.py`)
- Побудова графіка динаміки переглядів з 30-денною ковзною середньою (для згладжування шуму).
- Верстка лаконічного односторінкового PDF-звіту для керівництва:
  - Назва теми та аналізований період.
  - Таблиця ключових метрик (Total Views, YoY Growth, Reliability Score).
  - Візуальний графік трендів.
  - Продуктові висновки та застереження (Actionable Insights & Caveats).

### Етап 5: Створення `SKILL.md` та інтеграція для LLM
- Написання інструкції для агента за стандартом [Agent Skills](https://agentskills.io/specification).
- Опис CLI-команд, вхідних прапорців та прикладів поверненого JSON.
- Промпт-керівництво: як агенту відповідати користувачу, коли рекомендувати перевірку додаткових гіпотез та як пояснювати обмеження даних Wikipedia.

### Етап 6: Валідація та тестування на легких моделях
- Перевірка на тестових сценаріях із завдання:
  1. **Інтервальне голодування:** порівняння зростання в польськомовній та чеськомовній Wikipedia за 2 роки.
  2. **Астрономія:** аналіз україномовного розділу з оцінкою надійності тренду.
  3. **Вивчення англійської:** порівняльний звіт між декількома мовними розділами з рекомендаціями аудиторій.
- Тестування на моделях класу Claude Haiku 4.5 / безкоштовних моделях OpenRouter.
