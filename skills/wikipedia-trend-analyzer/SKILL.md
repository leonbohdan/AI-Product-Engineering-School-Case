# Wikipedia Trend Analysis Agent Skill

Ця навичка надає AI-агенту інструменти для детермінованого кількісного дослідження ринкового попиту та валідації гіпотез щодо локалізації B2C-продуктів (EdTech, Health & Fitness, мовні застосунки) на основі відкритих даних переглядів статей Вікіпедії.

---

## 1. Коли активувати цю навичку

Активуйте цю навичку, якщо користувач (фаундер, CPO або продакт-менеджер) запитує:
1. **Валідацію інтересу до теми:** *"Чи зростає інтерес до астрономії / нутриціології / йоги і наскільки цьому можна довіряти?"*
2. **Крос-мовне порівняння ринків:** *"Порівняй зростання інтересу до інтервального голодування в польській та чеській Вікіпедіях за останні 2 роки."*
3. **Пріоритетизацію локалізації:** *"Які ринки/мови для вивчення англійської варто дослідити першими та чому?"*
4. **Генерацію графіків або PDF-звітів:** *"Створи 1-сторінковий звіт для інвесторів/керівництва щодо тренду цієї теми."*

## 2. Як викликати навичку через CLI

Навичка запускається через єдиний уніфікований оркестратор [run.py](file:///home/bohdan/MyProjects/genesis-school/AI-Product-Engineering-School-Case/skills/wikipedia-trend-analyzer/run.py) з передачею прапорця `--json` для отримання структурованих числових аргументів.

```bash
# Крос-мовне порівняння кількох ринків (2 роки, з генерацією графіка та 1-сторінкового PDF)
.venv/bin/python3 skills/wikipedia-trend-analyzer/run.py \
  --topic "<назва теми>" \
  --langs "<мова1,мова2,...>" \
  --years 2 \
  --pdf \
  --json

# Дослідження однієї конкретної статті
.venv/bin/python3 skills/wikipedia-trend-analyzer/run.py \
  --article "<назва статті>" \
  --project "<мова>.wikipedia" \
  --years 2 \
  --pdf \
  --json
```

### Доступні аргументи CLI:
| Прапорець | Опис | Приклад |
| :--- | :--- | :--- |
| `--topic`, `-t` | Назва теми будь-якою мовою (автоматичний пошук через Wikidata) | `--topic "інтервальне голодування"` |
| `--langs`, `-l` | Цільові мовні розділи через кому | `--langs "pl,cs,uk,en"` |
| `--article`, `-a` | Точна назва статті (якщо відома) | `--article "Астрономія"` |
| `--project`, `-p` | Проєкт Вікіпедії (за замовчуванням `uk.wikipedia`) | `--project "uk"` |
| `--years`, `-y` | Глибина аналізу в роках (за замовчуванням `2`) | `--years 2` |
| `--override`, `-o` | Ручне перевизначення назв для конкретних мов | `--override "pl:Głodówka_lecznicza"` |
| `--pdf` / `--no-pdf` | Згенерувати 1-сторінковий PDF-звіт (увімкнено за замовчуванням) | `--pdf` |
| `--chart` / `--no-chart` | Згенерувати PNG-графік тренду (увімкнено за замовчуванням) | `--chart` |
| `--json` | Вивести чистий структурований JSON на stdout | `--json` |

## 4. Керівництво для AI-Агента: Як інтерпретувати метрики

Працюючи з даними навички, ви маєте пояснювати фаундеру бізнес-значення показників:

### 4.1. Метрика довіри (Reliability Score, 0–100%)
Індекс розраховується детерміновано за формулою з трьох компонентів:
- **Volume Factor (40%):** Обсяг вибірки. Якщо переглядів $< 30$ на день, високий ризик «проблеми малих чисел» (зростання з 10 до 20 переглядів дає штучні +100% YoY).
- **Stability Factor (30%):** Стійкість часового ряду через коефіцієнт варіації ($CV = \sigma / \mu$). Чим менша хаотичність, тим стабільніший попит.
- **Organic Factor (30%):** Відсутність новинного хайпу. Штрафує тренд, якщо левова частка переглядів сформована піками.

| Рівень | Діапазон | Що відповідати користувачу |
| :--- | :--- | :--- |
| **High** | **80–100%** | Тренд є статистично надійним і стабільним. Можна безпечно використовувати як первинний сигнал для розробки MVP або локалізації. |
| **Moderate** | **50–79%** | Помірний сигнал. Інтерес реальний, але або вибірка невелика, або є виражена сезонність/сплески. Обов'язково підтвердити зовнішніми джерелами. |
| **Low** | **0–49%** | Низька надійність. Трафік занадто малий (статистичний шум) або спалах був одноразовою подією (наприклад, новина в медіа). Спиратися на ці дані для інвестицій ризиковано. |

### 4.2. Зростання YoY vs Органічний YoY vs MoM
- **YoY Growth:** Порівнює сумарні перегляди за останні 365 днів з попередніми 365 днями.
- **Organic YoY:** Порівнює медіанний бейзлайн (очищений від аномальних піків). Якщо звичайний YoY показує +80%, а Organic YoY лише +5% — це означає, що «ріст» створений 2–3 днями медійного шуму, а не справжнім ринковим попитом.
- **MoM Growth:** Помісячна динаміка (останні 30 днів vs попередні 30). Допомагає побачити раптові розвороти тренду або початок шкільного/ділового сезону (наприклад, вересневий стрибок інтересу до навчання).

### 4.3. Новинні спалахи (Spikes & Outliers)
- Алгоритм виявляє дні, де перегляди перевищують $Q3 + 1.5 \times \text{IQR}$ (або $\text{Median} + 3 \times \text{IQR}$).
- Якщо `spike_impact_percent` $> 20\%$, обов'язково попередьте фаундера: інтерес аудиторії був викликаний ситуативними інфоприводами (наприклад, запуск ракети, затемнення, вихід вірусного шоу чи фільму).

### 4.4. Статті, яких немає у мовному розділі (`missing_languages`)
- Якщо в певному розділі статті за цією сутністю не існує (як-от для інтервального голодування у польській Вікіпедії), агент повинен інтерпретувати це не як технічний збій, а як **цінний ринковий сигнал**:
  - Відсутність термінологічного стандарту в мовному розділі.
  - Або слабка сформованість попиту, або пошук за іншими синонімами (наприклад, `Głodówka lecznicza` чи `Insulinooporność`).

У фінальній відповіді користувачу завжди дотримуйтеся чесності щодо обмежень даних Вікіпедії:
1. **Інтерес vs Платоспроможність:** Перегляди статей показують когнітивну зацікавленість, але не доводять готовність платити за підписку або застосунок.
2. **Демографічний перекіс:** Аудиторія Вікіпедії має певний ухил у бік студентів, школярів та людей, що шукають довідкову інформацію.
3. **Тріангуляція гіпотез:** Завжди рекомендуйте наступні кроки перед інвестуванням:
   - Перевірити пошукові запити з комерційним інтентом у **Google Search Volume** (Ahrefs / Google Keyword Planner).
   - Оцінити конкурентів в **App Store / Google Play** (Sensor Tower / AppMagic).
   - Запустити недорогий тест на попит (**Smoke Test / Landing Page** з попередньою реєстрацією).

## 6. Приклади для цільових сценаріїв кейсу

### Сценарій 1: Інтервальне голодування (PL vs CS)
**Запит:** *"Порівняй зростання інтересу до інтервального голодування в польськомовній та чеськомовній Wikipedia за останні два роки."*  
**Команда:**
```bash
.venv/bin/python3 skills/wikipedia-trend-analyzer/run.py \
  --topic "інтервальне голодування" \
  --langs "pl,cs" \
  --override "pl:Głodówka_lecznicza" \
  --years 2 \
  --json
```
**Висновки агента:**
- Пряма стаття у чеській Вікіпедії: `Přerušovaný_půst` (6,684 переглядів за 2 роки).
- У польській Вікіпедії окремої статті немає, найближча споріднена: `Głodówka_lecznicza` (5,823 переглядів).
- Чеський ринок наразі має дещо більший обсяг (53.4% сукупного попиту), але обидва ринки демонструють спад після ковідного піку. Довіра помірна (64/100 для PL, 51/100 для CS).

## 7. Обробка ітеративних запитів та уточнень користувача (Follow-up Flow)

Користувачі часто змінюють припущення або просять уточнити аналіз після отримання першої відповіді. Агент має підтримувати природний діалог:

### 7.1. Зміна часового горизонту
- **Запит користувача:** *"А що як подивитися за 3 роки замість двох?"*
- **Дія агента:** Перезапустити CLI з прапорцем `--years 3`. Порівняти довгостроковий 3-річний CAGR із 2-річним YoY, щоб перевірити, чи є поточний спад або підйом частиною більшого макроциклу.

### 7.2. Уточнення або заміна статті (`--override`)
- **Запит користувача:** *"У польській Вікіпедії стаття Głodówka lecznicza — це лікувальне голодування. А чи є стаття конкретно про інтервальне харчування?"*
- **Дія агента:** Пояснити, що у Wikidata для концепту `Q1666254` польський інтервікі-лінк відсутній. Пошукати кандидати через topic resolver або використати запропоновану користувачем назву:
  ```bash
  .venv/bin/python3 skills/wikipedia-trend-analyzer/run.py \
    --topic "інтервальне голодування" \
    --langs "pl,cs" \
    --override "pl:Post_przerywany" \
    --json
  ```

### 7.3. Додавання нових мовних розділів (Incremental Market Expansion)
- **Запит користувача:** *"Додай ще німецьку та іспанську мови до цього порівняння."*
- **Дія агента:** Доповнити список `--langs "pl,cs,de,es"`. У відповіді не дублювати весь попередній аналіз, а сфокусуватися на порівнянні нових ринків із вже проаналізованими (дельта за обсягом та динамікою).

## 8. Дорожня карта ітеративного розвитку навички (Scaling & Advanced Research)

Щоб навичка ефективно масштабувалася від базових точкових перевірок до складних масштабних досліджень ринку, передбачено наступні напрямки розвитку:

### 8.1. Семантична кластеризація тем (Topic Clusters & Category Trees)
- **Проблема:** Інтерес до однієї головної статті (наприклад, `Астрономія`) може стагнувати, тоді як супутні прикладні теми (`Джеймс Вебб`, `SpaceX`, `Астрофотографія`, `Марсохід`) стрімко зростають.
- **Розвиток:** Інтеграція з **Wikimedia Category API**. Автоматичний збір дерева підкатегорій (depth=2), обчислення зведеного індексу категорії (Category Trend Index) та побудова теплової карти (Heatmap) зростання субтем.

### 8.2. Пакетна обробка великих масивів даних (Bulk / Big Data Processing)
- **Проблема:** Аналіз сотень тем або мов через REST API може впиратися в мережеві затримки та ліміти (HTTP 429).
- **Розвиток:** Використання публічних **Wikimedia Daily Pageview Dumps** та **Clickstream Data** (переходи між статтями). Локальне завантаження parquet/dump-файлів через DuckDB або Apache Arrow для миттєвого скорингу тисяч тем без звернення до мережі.

### 8.3. Тріангуляція з комерційними сигналами (Multi-Source Triangulation)
- **Проблема:** Вікіпедія відображає інформаційний інтерес, але не платоспроможність.
- **Розвиток:** Інтеграція додаткових конекторів:
  - **Google Trends / Search Console API:** Комерційний інтент (пошукові запити «купити», «курси», «додаток»).
  - **App Store / Google Play Scraping (AppMagic / Sensor Tower):** Кількість завантажень та виручка конкурентів у вибраних географіях.
  - **Reddit / HackerNews Sentiment:** Тональність обговорень та скарги користувачів на існуючі продукти.

### 8.4. Прогнозування та декомпозиція часових рядів (Forecasting)
- **Розвиток:** Впровадження моделей статистичного прогнозування (**Prophet** або **Statsmodels STL**) для виділення сезонності (наприклад, регулярний вересневий шкільний стрибок) та побудови довірчого інтервалу тренду на наступні 6–12 місяців.

## 9. Оптимізація під швидкі та недорогі моделі (Claude Haiku 4.5 / OpenRouter Free)

Ця навичка спроєктована за принципом **«Deterministic Compute, Semantic Reasoning»**:
1. **Нульове витрачання токенів на сирі дані:** Замість передачі в контекст LLM 730 рядків числових переглядів (понад 15 000 токенів), CLI обчислює всі статистичні показники локально і видає компактний JSON розміром $\approx 600$ байт.
2. **Передбачуваність і детермінованість:** Навіть найлегша модель отримує готові поля `reliability_score`, `organic_yoy_percent` та `spike_impact_percent`, що усуває математичні галюцинації.
3. **Економія пам'яті:** Повний контекст діалогу залишається легким, дозволяючи агенту проводити тривалі ітеративні сесії без деградації якості відповідей.
